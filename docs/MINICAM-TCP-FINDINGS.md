## 已确认与未确认

这次长停顿的直接机制是服务器至模组 TCP 之间的缺段/未确认、拥塞窗口收缩及重传退避；可靠有序传输因此阻塞后续语音。与 RFC 6298 的重传退避机制一致：https://www.rfc-editor.org/rfc/rfc6298.html 。ESP32 Opus/I2S 不是这次长停顿的首要证据位置，增加缓存或降低码率无法让缺失 TCP 字节绕过队首阻塞。

仍不能区分无线覆盖/干扰、运营商或 APN 路径、路径 MTU/分片、大包处理、模组 TCP 固件等具体原因。反向反馈正常不证明下行正常；snd_wnd 非零也不能证明模组所有处理都正常。只看统计无法断言是路径 MTU 黑洞。

## 下一项可回滚对照

`deploy/probe-cellular-mtu.sh` 在 Caddy 网络命名空间内，仅为指定的模组公网 IPv4 增加一条临时 /32 路由，MTU 默认 900，采样三分钟后删除。它不改主机默认路由、不覆盖已有 /32、不改 TLS 或设备。该公网 IP 若由多个设备共享，测试会影响这个命名空间到同一 IP 的其他连接；不要误当作单设备精确匹配。

该测试检查“大包/路径 MTU”假设，不是已经验证的修复。不设置 mtu lock，不强迫 IP 分片；必须查看 ss 的实际 mss/pmtu 是否下降，未下降则不是有效的小包对照。若现有连接未采用新路径，另安排受控重连，并核对设备公网 IP 没有变化。测试前保持当前码率、固件、位置和天线不变。

```bash
sudo bash deploy/probe-cellular-mtu.sh PEER_IPV4 180 900 > /tmp/voxi-small-mtu.txt
```

PEER_IPV4 从本轮 ss 的 Peer Address 取得，不保存设备实际公网地址到公共仓库。脚本正常结束、INT/TERM/HUP 都尝试删除自己新增的路由；SIGKILL 或整机崩溃无法触发 shell trap，届时按打印的目的地址检查 proto 186 的 /32 路由。Caddy 容器网络命名空间被销毁时临时路由也消失。

脚本已在用户服务器执行，首轮结果见下节。若多轮小包测试仍显著降低相近长度回复的重传与 RTO，则进一步查 MTU/分片/大包处理；若无稳定改善，优先另一运营商 SIM、位置/天线和模组固件的单变量对照。UDP/PLC 路线有不同丢包和安全语义，不在这次未经验证地切换。

路由 MTU 与 TCP 统计字段依据：https://man7.org/linux/man-pages/man8/ip-route.8.html 、https://man7.org/linux/man-pages/man8/ss.8.html 。

### 后续实现边界与对照

中移物联网《TCP/IP 用户手册 V5.0.0》适用型号包含 ML307R-DC/DL，3.1 节列出了 `MIPCFG` 的配置项，但未列出 MSS/MTU 设置。当前本地 esp-ml307 源码也未提供该项；这表示尚无已核实的设备侧设置方法，不能断言所有固件都不支持，更不能猜一个 AT 命令写入实机。`sndbuf`、`rcvbuf` 是缓存参数，不等价于 TCP MSS。手册原文：https://m5stack-doc.oss-cn-shenzhen.aliyuncs.com/1189/TCP_IP_User_Manual_V5.0.0.pdf 。

1. 固件与码率保持当前基线；固定位置、天线和回复提示词，重复 MTU 900 的长回复测试，再做默认路径对照。尽量匹配实际音频时长，并记录起播目标；每种条件使用受控的新连接，核对实际 PMTU/MSS，避免旧连接的小 MSS 残留污染默认组。
2. 先验证几十秒断流是否稳定消失，再处理短耗尽及首音延迟。不要继续靠增加起播缓存掩盖问题，也不要因单轮改善立即降低门槛。
3. 若确认需要产品化的小包策略，优先核实模组当前固件的接收 MSS 能力；否则评估独立蜂窝入口上的连接级发送策略。公网 IP 会变化且可能共享，当前临时 /32 路由仅用于诊断，不作为长期设备配置。
