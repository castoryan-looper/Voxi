# 下行播放缓存与蓝牙移除（2026-11-03）

## 当前变更

本地固件不再引用 BLE 实现，不创建蓝牙任务、队列或初始化 BLE 协议栈。旧版网页发出的 bluetooth_* 请求返回 410；状态明确报告 disabled。管理页移除蓝牙配对控件。有线旋钮继续由 main.cpp 的 GPIO 编码器处理，NVS 中的原配对记录不主动删除。

注意：原实现仅在已有配对或发起扫描时启动蓝牙，未配对时不能假设立即省出 12KiB 任务栈。实际收益需烧录后测量，不能从源码估算当成实测值。

## Flash 下行缓存可行方案（尚未实现）

链路：云端 PCM → 有限 RAM 写入队列 → LittleFS 独立回复文件 → RAM 预读缓冲 → I2S DMA → 扬声器。

边接收边播放，不必等待整句下载。24kHz/16bit/mono 为 48000B/s，2MiB 约存 43.7 秒。现有 storage 分区约 11.94MiB，但需扣除录音文件、元数据、可用空间和清理余量；应从运行时可用空间决定容量，不能直接占满分区。

录音和回复文件必须分开；明确只有已写完的数据可读。文件写入/清理应由存储任务负责，不能在播放主循环逐帧同步写文件。维持几百毫秒 RAM 预缓冲，记录最大写入/读取耗时、排队水位、总接收/播放字节与完整性。下载超过文件上限、空间不足或写入失败时应可见地结束本轮，不能悄悄丢音频或无限占用空间。

现有录音缓存迁移逻辑只识别 voxi-turn.pcm；引入新文件时需一起审查挂载、清理、并发和版本兼容。原录音缓存以 capturing 期间不可上传读取为约束，不可直接当作并发下行缓存复用。

Flash 不是 RAM：写入/擦除可能影响执行时延，存在磨损。需连续长回复和弱网测试；仍需云端限制突发下发速度与排队大小。该方案尚未改动分区或烧录，不是已完成的溢出修复。

## 本轮验证

20 项 Node 网关/管理页测试通过，固件编译通过，COM10 烧录并校验成功。设备 READY，bluetoothEnabled=false；配置编号 0DB36B4F 保留，Wi-Fi 与音量 50 保留，无新故障。READY 空闲堆 90484B、启动至此最低 79792B；此前旧固件运行约三小时的样本为 53524B / 25812B。运行时间不同，差值不可直接等同于蓝牙移除收益或长期最低内存。Flash 下行缓存未实现，本轮不声称播放溢出已解决。代码仅本地修改，未推送云端。

## 2026-11-03 长故事卡顿修复

修复前同一轮收到3508800B（约73.1秒PCM），playbackRebuffers=8、replyGapMaxMs=1286，播放写入错误0，无本轮turnFailure。此前的Pocket connection reset为上一轮保留故障，不可直接用作本轮原因。

RAM播放容量从57600B提高到96000B（2秒）；默认起播水位从500ms提高至1400ms，断流后逐步提高至1700ms。220ms提示音加最高预缓冲仍小于2秒容量。代价是默认首段起音约多等待900ms。

播放服务每轮最多尝试写入6个10ms音频块，在DMA满时立即退出，只有实际写入的样本才从环形缓冲消费；不改变采样率和音频内容。增加playbackPeakMs/playbackServiceGapMaxMs诊断，管理页显示容量及播放服务最大间隔。

验证：固件编译、USB烧录与写入校验通过；播放门控C++回归通过（覆盖1.28秒无新包时仍有待播音频，以及短回复尾音排空）；11项管理页测试通过。实机容量2000ms、水位1400ms，配置编号与音量保留。尚未完成修复后的真实长故事听测，不承诺任意更长网络停顿都无卡顿。本轮未实现Flash下行缓存。

烧录后曾遇Pocket握手HTTP503，自动重试后已恢复READY；READY空闲堆51192B、最低42508B，配置保留。该503不能直接当成上一轮周期性卡顿根因。

## 2026-11-03 捕获缓冲耗尽后的集中补包溢出

实时USB采样捕获：2535s开始回复，2572s进入BUFFERING（缓冲耗尽计数1，目标1550ms），2573s播放缓存峰值达到2000ms并报 Reply playback buffer overflow，随后OFFLINE并重连。收包最大间隔1117ms，播放服务最大间隔32ms。证据说明同轮先耗尽、后溢出，不能继续仅扩大RAM。

修复：Pocket代理增加PCM下发节奏控制（960B/20ms），网络暂停后不累计可突发发送额度；音频与audio_end/ready保持顺序，取消/换台清理旧音频。TCP发送缓冲较高时暂停发送。云端仅限制待发积压30秒（1.44MB），不是故事总时长上限；超过积压上限会明确报错，不静默丢音频。

固件在有效PCM帧暂时放不进播放缓冲时，将其保留在有界接收队列中，先播放已有样本。网络任务在接收队列空间不足时暂停ws.loop读取，让TCP传播反压；仍然保留格式错误/异常超大帧保护。无Flash写入，不扩RAM，不丢掉装不下的音频来假装流畅。

验证：24项Node测试通过，包括集中补包整形、暂停后不突发、PCM逐字节一致、结束标记有序、取消、积压上限及总时长独立性；固件编译通过。生产端仍需更新Voxi并实测长故事；本轮不承诺任意断网时都能不中断。

## 链路断开诊断版

用户贴回的生产日志：2026-11-03 13:32:13.496 UTC设备连接1006关闭，约43ms后Pocket连接1000关闭；两个容器restart=0、oom=false。只能定位设备到Voxi链路先断，不能从1006判断是Wi-Fi/TCP还是心跳主动终止；HTTP503发生在随后的重连，不可当作初始原因。

设备增加持久到下次启动的wifiDisconnectedAtMs/wifiConnectedAtMs/wifiDisconnectReason/wifiDisconnectCount；wifiDisconnectedEpochMs在时间同步后可与服务端UTC日志对照（秒精度）。gatewayDisconnectedAtMs、lastWsPingAtMs/lastWsPongAtMs和计数定位心跳；rxBackpressureMaxMs记录接收队列暂停读取的最长持续时间。不记录SSID、密码、token或音频内容到这些新增诊断字段。

网关增加device_opened事件；device_closed记录主动关闭origin、连接时长、ping/pong计数与间隔、PCM待发积压、TCP发送积压；主动心跳终止前输出device_heartbeat_timeout。pocket_error/pocket_closed/session_rotation也明确标注。不修改原有超时或心跳策略。

操作：更新Voxi服务后，先等设备READY；复现一次长故事卡顿/offline后不要开启新一轮，也不要重启设备。保留两容器最近10分钟带时间戳日志和设备status。若先有wifi断开时间则查本地Wi-Fi链路；若有device_heartbeat_timeout而无Wi-Fi断开则结合接收反压和心跳计数定位；若origin=pocket_closed或pocket_error则继续查上游。peer_or_transport仍不能单独区分TCP中断的根因。

本轮24项网关测试与固件编译通过。该版本只增强诊断，不声称已修复新出现的链路断开。
