# 2026-11-03 实机延迟分析

范围：保持录音后上传、云端实时 RTP、500ms 起播缓冲和 220ms 开台声策略不变。用户报告第一次录音失败，其后两轮成功。只有两个成功样本，不能据此估算 P95 或稳定成功率。

| 阶段 | 短录音 | 长录音 |
|---|---:|---:|
| 实际 PCM 录音时长 | 4.670s | 10.630s |
| 长按确认后提示音与麦克风保护 | 0.321s | 0.321s |
| 松手到开始上传 | 0.017s | 0.022s |
| 上传开始到本机写出 ptt_up | 3.231s | 6.937s |
| 写出 ptt_up 到收到首段回复 PCM | 7.753s | 12.351s |
| 首段 PCM 到首次写入回复人声 | 0.612s | 0.596s |
| 松手到首次写入回复人声，总计 | **11.613s** | **19.906s** |
| 云端提交录音到回复起点 | 7.584s | 12.251s |
| 回复起点时已交给 RTP track 的音频时长 | 5.470s | 11.430s |

最后一项含现有 0.8s 尾部静音，两轮在回复开始前均已将队列送完。设备与服务器各用本地单调时钟计时；未跨设备直接相减时间戳。首次人声写入 I2S 不是实际扬声器声压起点，后者还受最多约 60ms DMA 排队影响。时间来自程序事件，不是 ASR 完成时间。

结论：上传与提交后等待占总等待的约 95% / 97%；播放前等待只占约 0.6 秒。上传有效速度约 69KB/s / 74KB/s。录音越长，上传和服务器实时送音频的等待越长。云端数据证实存在“松手后再按实时速度送一遍录音”的成本；不能把服务器的整个等待都归因于模型计算。优先考虑将录音、上传和 RTP 输入重叠，保留 Flash 弱网缓存；其次研究协议支持的结束方式。减小播放缓冲不是主要收益来源，且会增加卡顿风险。此轮未实施这些优化，也未承诺优化后的具体响应时间。

异常单独记录：第一次失败的最近错误为 WebSocket send failed TLS=48 UNKNOWN ERROR CODE (0030)，具体 TLS 底层原因未确认，不计入成功样本平均值。长轮回复最终出现 1 次重新缓冲，短轮采样时为 0，未取得短轮结束后的完整缓冲统计。用户报告黑屏闪动但音频正常；设备启动次数为 1，结合固件每 60 次有效画面变化触发全刷的代码，与墨水屏全刷现象一致，不应视为重启证据。


## 并行上传迭代实测

旧版成功样本为 10.63 秒录音、松手后上传 6.937 秒、松手到人声写入 19.906 秒。并行上传的一次成功样本为 11.25 秒录音（540000B），松手时已发送 539520B（99.91%），松手后的上传收尾为 0.246 秒，提交到回复首包 13.654 秒，首包到人声写入 0.817 秒，总计 14.717 秒。录音内容、时长和模型响应不同，不能将单次差值当作稳定收益或 P95；可以确认此成功样本几乎完全隐藏了上传等待。云端仍在松手后按实时速度送出 12.05 秒录音加静音，仍是主要剩余成本。

用户同时报告成功前两次失败，不能忽略失败样本只报告第三次成功。因此随后增加了未提交录音的一次缓存重传，以及更准确的发送错误诊断；需继续观察其真实对话恢复效果。上述并行成功样本在回复期间有1次重新缓冲，并非卡顿已完全消失。


最终固件已迁移自有缓存到 LittleFS，连续两轮 20 秒合成正常链路测试均通过：每轮 960000B，CRC32=2784024299，uploadRetries=0，停止采样后完整上传分别为14ms和15ms；最大缓存写入46ms/59ms，文件收尾9ms，缓存清理3ms/5ms，均未报告发送错误。测试允许一次恢复但没有触发恢复，因此它不能替代实际断网下的恢复验证；未提交后恢复、提交尝试后禁止重放的边界另由 C++ 单元测试覆盖。合成测试不发送 ptt_up 给模型，不能视为两轮真实识别/回复测试。迁移前的裸链路测试仍发现过写超时；不能从两个成功样本声称底层网络问题彻底消失。
